# ADR-001: Repository Pattern, Error Translation, and Firestore Security for Study Notes

**Date:** 2026-11-11  
**Author:** Efe Sarp Ayaz  
**Milestone:** Lab 5 / P1 / P2 / P3 / P4  
**Tool and model used:** OpenCode + big-pickle

## Context

The Study Notes app (COMP 205 Lab 5) must sign users in and out and read/write
per-user notes in Cloud Firestore with live updates, while staying testable offline
(CI uses fakes) and secure (each user may touch only their own notes). Calling the
Firebase SDKs directly from widgets would couple the UI to Firebase, leak
`FirebaseAuthException` codes into the interface, and make tests depend on a real
project. We needed a clean data-access boundary plus a consistent approach to error
mapping, secret handling, and access control.

## Prompt

```
Study Notes (Flutter + Firebase) lab: implement Part 1–4 with the Repository pattern —
Note model (fromFirestore/toFirestore), AuthRepository (signIn/signUp/signOut and
FirebaseAuthException -> AuthFailure via messageFor), NotesRepository (watchNotes stream,
addNote with title validation, deleteNote), and NotesScreen (StreamBuilder + Dismissible
list). Add Firestore rules so a user can only access users/{uid}/notes/*, and explain the
decisions for the ADR.
```

## Result

- **`lib/models/note.dart`** — `Note.fromFirestore` validates that `title` and `body` are
  `String` (otherwise `FormatException`) and maps `createdAt` from a `Timestamp`
  (nullable); `toFirestore` writes `title`, `body`, and
  `createdAt: FieldValue.serverTimestamp()` and never the id (the id is the document id).
- **`lib/data/auth_repository.dart`** — `signIn`/`signUp` trim the email, catch
  `FirebaseAuthException`, and rethrow `AuthFailure(messageFor(e.code))`; `signOut`
  delegates to `FirebaseAuth.signOut`; `messageFor` is a switch expression over the
  documented codes.
- **`lib/data/notes_repository.dart`** — `watchNotes` =
  `orderBy('createdAt', descending: true).snapshots().map(...)`; `addNote` trims
  title/body and throws `ArgumentError` for an empty or >100-character title;
  `deleteNote` deletes by document id.
- **`lib/screens/notes_screen.dart`** — `StreamBuilder` over the repository stream with
  error / spinner / empty / list states; each note is a `Dismissible(key:
  ValueKey(note.id))` calling `deleteNote`; the FAB opens `AddNoteDialog`.
- **`firestore.rules`** — per-user `read`/`delete` and `create`/`update` with a valid
  1–100-character string title.
- **Secrecy** — `firebase_options.dart` and other sensitive data live in `.gitignore`
  and were never pasted into prompts or committed.

Key diff (error translation):

```dart
} on FirebaseAuthException catch (e) {
  throw AuthFailure(messageFor(e.code));
}
```

## Rejected suggestion(s)

1. The first AI draft of `messageFor` returned `'the email address is not valid.'` for
   `invalid-email`, but `lab05_test.dart` expects `'The email address is not valid.'`
   (capital T). The suggestion was **rejected because it failed the provided test**; the
   string was corrected to the exact expected casing.
2. The AI initially produced a generic ADR (Title/Context/Decision/Consequences) instead
   of this repository's `ADR-000-template.md` (AI Decision Record) layout. That format was
   **rejected because the course requires the template**, so this ADR was rewritten to
   follow it.

## Verification

- `flutter analyze` reports **No issues found** for the whole project.
- Behaviour is checked against the provided suite `test/lab05_test.dart` (Parts 1–4) with
  `FakeFirebaseFirestore` and `MockFirebaseAuth`, so no real Firebase project is needed;
  `flutter test` is run once Parts 3–4 are filled in.
- Firestore rules will be validated by deployment and a manual two-user check (user A
  cannot read or write user B's `users/{uid}/notes/*`).

## What I learned

Wrapping Firebase behind repositories keeps the UI thin and makes the data layer
verifiable with fakes, and translating SDK exceptions into a small domain type
(`AuthFailure`) prevents Firebase-specific codes from leaking into the UI. Exact test
expectations — including message casing — are part of the contract and must be matched
precisely.
