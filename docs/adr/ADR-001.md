# ADR-001: Repository Pattern with Firebase for Study Notes

**Date:** 2026-11-11  
**Milestone:** Lab 5  
**Status:** Accepted

## Context

The Study Notes app must authenticate users (sign-in, sign-up, sign-out) and manage
per-user notes stored in Cloud Firestore, showing changes live while keeping the code
testable and secure. Calling `FirebaseAuth` and `FirebaseFirestore` directly from the
widgets would couple the UI to Firebase, leak SDK error codes into the interface, and
make unit/CI testing depend on a real project. We therefore needed a clean boundary
between the UI and the Firebase services, plus a clear approach to error handling,
secrets, and access control.

## Decision

- **Repository pattern.** UI code depends on `AuthRepository` and `NotesRepository`
  rather than on the Firebase SDKs. `NotesRepository.watchNotes` exposes a
  `Stream<List<Note>>` consumed by a `StreamBuilder` for live updates; `addNote` and
  `deleteNote` encapsulate writes. Widgets read repositories through `Provider`.
- **Error translation.** `AuthRepository` catches `FirebaseAuthException` and rethrows
  a domain `AuthFailure` whose message comes from a centralized `messageFor(code)`
  mapping, so the UI never sees SDK-specific codes.
- **Security and secrecy.** `firebase_options.dart` and other sensitive data stay in
  `.gitignore` and were never pasted into prompts or committed. Firestore security
  rules restrict `users/{uid}/notes/*` so that a signed-in user can read, create,
  update, and delete only their own notes (writes additionally require a valid
  title of 1–100 characters).
- **Testability.** FCM is isolated behind `MessagingService`, and Firebase services are
  replaced with `FakeFirebaseFirestore` and `MockFirebaseAuth` in unit and CI tests,
  so the suite runs without a real Firebase project.

## Consequences

- **Positive:** Clear separation of concerns, a mockable/fakeable data layer, live UI
  via streams, consistent user-facing error messages, and defense-in-depth with
  per-user security rules and no secrets in source control.
- **Trade-offs:** An extra abstraction layer and mapping code to maintain; the app
  remains dependent on Firebase's data model (`Timestamp`, `FieldValue`); rules must be
  deployed separately from the app; fakes can drift from real Firebase behavior, so
  integration checks on an emulator are still required.
